# T-206 — Service worker y app shell offline

**Proyecto:** ASTRA HEALTH · **Responsable:** Benito (reasignado por Bruno, 15 nov; originalmente Justin); revisa Bruno · **Fase:** MVP · **Fecha:** 15 nov 2026
**Fuente:** TASKS.md T-206; D-26 (`vite-plugin-pwa` autorizado); PROJECT_SPEC.md §6.1 y §11; ARCHITECTURE.md §3; TEST_PLAN.md QA-107.

**Rama:** `t-206-service-worker`.

## 1. Objetivo

Que la app **abra al recargar sin conexión**: después de cargarla una vez con conexión, un **service worker** guarda la "cáscara" de la app (HTML, JS, CSS e íconos). Si se pierde el enlace y se recarga la página, la app abre igual y la nave sigue viendo sus datos, que están en IndexedDB.

Es el **paso 7 del guion de la demo** ("recargar sin conexión y recuperar todo") y **QA-107**.

## 2. Alcance permitido

- `apps/web/vite.config.ts`, `apps/web/package.json` y `package-lock.json`.
- Si hace falta un ícono o un manifest: `apps/web/public/`, pero el **manifest es opcional** (PROJECT_SPEC §11).
- **No tocar:** `apps/web/src/` (Justin y Bruno trabajan ahí; **ni siquiera `main.tsx`**), `apps/api/` ni `packages/`.
- **Única dependencia nueva permitida:** `vite-plugin-pwa` (D-26), como `devDependency` y **con versión exacta**.
  - Antes de instalar, comprobar que esa versión declara compatibilidad con **Vite 8** (sus `peerDependencies`).
  - **Si no hay una versión compatible, detenerse y avisar.** No forzar con `--force` ni `--legacy-peer-deps`.

## 3. Criterios de aceptación

1. **`VitePWA` en `vite.config.ts`**, con la estrategia `generateSW`:
   - **Registro sin tocar el código:** `injectRegister: "script"` o `"auto"`, para que el plugin agregue el registro al HTML del build. Así no se edita `main.tsx`.
   - **`registerType: "autoUpdate"`**, para que cada build nuevo reemplace al anterior sin preguntar.
   - **Precache del app shell:** `globPatterns` con `**/*.{js,css,html,svg,woff2}`.
   - **`navigateFallback: "/index.html"`**, para que una recarga sin conexión abra la app.
   - **Sin caché de datos:** ningún `runtimeCaching` para la API. Los datos dinámicos viven en IndexedDB (PROJECT_SPEC §11). La API corre en otro puerto (3000), así que el service worker no debe interceptarla.
   - **Sin service worker en desarrollo** (`devOptions.enabled: false`). Solo existe en `npm run build` + `npm run preview:web`.
2. **Sin recursos externos:** todo sale del build. Las tipografías ya son del sistema (T-103).
3. `npm run build` genera `dist/sw.js` (y el archivo de Workbox). Las pruebas actuales siguen en verde.

## 4. Verificación manual (QA-107; es la prueba que cuenta)

Con `npm run build`, `npm run start:api` y `npm run preview:web`, en **Firefox**:

1. Abrir **http://localhost:4173/?role=ship** **con conexión**. En F12 → **Aplicación** (o **Almacenamiento**) → **Service Workers**, debe aparecer uno **activo** para `localhost:4173`.
2. F12 → **Red** → cambiar **"Sin limitación"** por **"Sin conexión"**.
3. **Recargar con F5.** La app **debe abrir**: la barra lateral, los rótulos y las pantallas. **No** debe salir la página de error de Firefox.
4. En la pestaña **Red**, las peticiones a `localhost:3000` (la API) **fallan**, y es lo esperado.
5. Volver a **"Sin limitación"** y recargar: todo normal.

📸 Capturas: el service worker activo y la app abierta en modo "Sin conexión".

**Aviso para todo el equipo:** con el service worker activo, el navegador puede seguir mostrando un build **viejo**. Si después de un `npm run build` no se ven los cambios: F12 → Aplicación → Service Workers → **Unregister** y recargar.
